# Spec：内置管理 QQ 组件与图形化连接

状态：Done；2026-11-04。独立验收 PASS；真实 Mac Docker 验证至二维码和清理，账号收发与 Windows/Linux 实机仍待验。

## 背景
用户要求把 NapCat 的准备、登录和配置纳入 Desktop，并指出现有 QQ 页面要求填写过多内部参数、信息混杂。用户已确认管理原版 NapCat，由大肥鱼实现界面与适配，不修改或公开发布 NapCat 源码。

## 目标
用户通过大肥鱼的图形界面准备 QQ 组件、扫码登录、指定主人和回复范围；程序负责内部连接参数与组件生命周期。

## 非目标
不复制 NapCat Desktop 的 GPL 实现，不更换大肥鱼技术栈，不重写 QQ 协议，不自动登录或代用户扫码，不自动发真实消息，不改变主动发送审批、群聊记忆隔离或主人识别规则。

## 当前行为
用户需独立安装 NapCat、设置 OneBot，再手填地址、token、机器人 QQ、主人 QQ 和群号。页面同时显示启用开关、权限、说明、消息记录及审批入口；Runtime 不负责 NapCat 安装、登录和进程。

## 目标行为
- 默认入口为组件准备、扫码登录和账号状态；已经配置外部服务的用户保留现有连接方式。
- 管理模式内部生成端口和凭据；机器人 QQ 从已验证的登录信息获取，只读展示。
- 主人由本机用户明确指定，允许回复的群明确选择，均不得凭昵称、自称或扫码者身份推断。
- 主操作统一为准备、登录、启用/停用；回复范围与主动消息、历史记录分层呈现。
- 保留折叠的「连接已有服务」，其中才显示外部地址和凭据；不以删字段破坏既有配置。

## 功能需求
1. 管理固定来源、固定版本的原版 NapCat；安装失败可重试，展示实际状态，不以下载或进程存在冒充账号在线。
2. QQ 数据与日常 QQ 隔离；只管理本实例拥有的资源，不扫描或终止用户其他 QQ / NapCat 进程。
3. 登录状态、二维码、账号及必要的错误在大肥鱼内呈现；二维码刷新由真实上游接口完成。
4. 本机内部服务仅监听回环，自动生成凭据，不在界面、日志、状态接口输出秘密。
5. 好友和群列表通过只读接口获取，供用户指定主人和允许群；保留必要的 ID 输入兜底，不自动扩大权限。
6. 配置改变、账号变化、停用与 Runtime 关闭遵循现有撤权和在途任务取消语义。
7. UI 使用现有 beUI 组合组件与浅海蓝主题，字段 16px、分组 24px、操作 8px 的现有间距规则保持；窄屏无横向溢出。
8. 安装、启停、刷新和配置错误走统一反馈；轮询不覆盖未保存表单、不重复弹出同一错误。
9. macOS/Linux 通过 Docker 管理隔离的原版组件；Windows 适配独立原生组件。首次使用按需下载固定版本，缺少 Docker 时明确说明所需环境，不静默安装系统软件。不得修改系统 QQ、共用日常 QQ 账号数据或更改系统安全设置。

## 边界条件
网络下载失败、缺少运行环境、端口冲突、重复启动、二维码过期、登录未完成/需验证、登录账号变化、组件崩溃、停止与安装/登录并发、已有外部服务配置、无好友/群列表、Runtime 重启及数据迁移后的失权。

## 技术约束
沿用单根 npm、普通源码模块、Runtime 统一管理平台状态，Desktop/Web 只调用认证 API。新增模块按实际职责封装于现有 channels 区域，不建立新包或第二套治理结构。所有上游接口与安装命令以固定源码和官方产物为据。

## 兼容性要求
既有 OneBot 配置、CLI、平台插件与审批兼容；既有模型和聊天数据保留。平台能力须如实显示；未进行 Windows 实机或真实 QQ 账号测试不得写为完成。
