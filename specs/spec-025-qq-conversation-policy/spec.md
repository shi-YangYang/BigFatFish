# Spec：QQ 多好友、群聊触发与直接发送

状态：Done；2026-11-04，R1 新独立验收 PASS。

## 背景
用户确认 QQ 能回复，要求说明「我的 QQ」、群聊无需 @ 也能回复，并删除 QQ 主动消息审批。随后明确：多个好友可私聊，但「主人」只能有一个 QQ。

## 目标
将主人身份与私聊范围分开，支持群内普通消息触发，QQ 主动消息直接发送并展示实际发送记录。

## 非目标
不移除抖音等独立业务审批，不改登录/安装器，不拓展任意 OneBot 操作，不自动给全部联系人授权，不操作真实 QQ 或发送测试消息给真人，不新增社交调度策略。

## 当前行为
ownerId 同时代表唯一主人和唯一私聊允许对象；授权群强制需要结构化 @。QQ 主动发送、B站分享到QQ、CLI和插件 channel.propose 均通过 QQ ApprovalStore。前端顶栏和养成页合计 QQ/抖音审批。

## 目标行为
- 「主人 QQ」只能选择或填写一个账号，保留主人识别和私密记忆。机器人账号不能作为主人。
- 「可私聊的好友」可多选、联系人不可用可手填多个 QQ 号；主人始终可私聊，不必重复加入好友列表。其他未选账号不回复。好友不因能聊天而被当成主人，仅能使用已共享记忆。
- 允许群仍须明确选择；群聊触发方式为「普通消息也回复」或「仅被 @ 时回复」，按本次明确需求默认普通消息也回复，包括旧配置缺省此字段。自身消息、未选群、重复事件等保护保持。
- 开启主动消息后，可向主人、已选好友或允许群直接发送。取消创建/批准/拒绝/过期等 QQ 审批流程；展示发送中、已发送、失败、结果未知等真实记录，未知结果不自动重试。
- B站分享到QQ、CLI及获相应权限的插件使用同一直接发送服务。QQ从全局待审批计数/抽屉移除；抖音审批保持。

## 功能需求
1. 在 Runtime 统一解析、持久保存并复核主人、好友、群和触发方式。托管/已有服务入口共享约束，保持 revision 和草稿保护。
2. 旧配置缺少好友列表时为[]，保留原 ownerId；保留已有会话和记录，不将好友赋予主人受众。配置修改仍阻止旧在途生成/外发。
3. 直接发送替代 QQ 审批服务，认证、渠道开关、主动开关、目标范围、插件权限、媒体校验和最终外发检查保持；停用/撤权/账号变化与调用方取消仍能拦截尚未发出的动作。
4. 新直接发送接口和 CLI 命令语义明确；旧审批写入口须明确报已移除，不能把过去的「提案」请求悄悄解释成发送。旧待审批数据不自动发送或重放，无需删表/删历史；共用 ApprovalStore 保留给其他模块。
5. 新插件 channel.send 权限与旧 channel.propose 区分，旧提案授权不自动升级为可直接外发；已废弃接口明确报错。更新关联 SDK/文档/相关现有测试，不维护可用的 QQ 审批旁路。
6. 使用当前 beUI/浅海蓝及 Spec024 紧凑分组；主人、好友、群三个概念清楚，直接发送按钮和结果不再出现审批文案。

## 边界条件
联系人缺失/手填、多选、主人同时出现在好友列表、自身账号、未授权私聊/群、被 @ 与普通消息、重复消息、共享记忆撤销、配置变更竞态、主动关闭、发送失败/未知、旧审批调用和历史待审批项、跨入口相同发送语义。

## 技术约束
普通源码模块，不拆包、不新增依赖、不修改数据库 schema。主 Agent 维护规格和决策，一个实施 Agent 串行处理耦合改动，新的独立验收。测试仅用隔离 OneBot/模型/数据；不重启用户当前登录的 Runtime。

## 兼容性要求
配置新增字段可缺省读取；新发送契约应清楚区分请求已接受与外部协议确认，并沿用持久交付记录及不自动重试语义。审批接口被移除是用户批准的业务变化，调用方全部迁移或返回明确废弃错误，不静默改变旧请求副作用。

## 验收标准
- [x] 唯一主人与多个可私聊好友独立配置，UI、托管/外部API和持久化一致；旧配置可读取。
- [x] 好友私聊被回复但没有主人记忆/身份，未选用户拒绝；主人私聊原行为保持。
- [x] 允许群普通消息能触发，可切回仅@；自身/未选群/重复事件不误回复。
- [x] QQ主动发送不需审批，UI/CLI/B站/插件链路一致，旧提案不会被自动发出。
- [x] 撤权/停用/取消/媒体/未知结果及共享记忆边界保持，发送记录可查；抖音审批不受影响。
- [x] 相关检查及桌面/窄屏 UI 通过，独立验收PASS，按持续授权本地commit。

## 待确认问题
无。用户已明确多好友与唯一主人；取消审批按当前QQ语境处理，其他平台保持。
